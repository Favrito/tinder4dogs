# Research & Design Decisions

## Summary

- **Feature**: `mutual-match-detection`
- **Discovery Scope**: Extension (light discovery — integration-focused, no new runtime dependencies)
- **Key Findings**:
  - The existing `match/` package contains **scoring**, not matching. The product noun "match" is unused in code, but `MatchResponse` is already taken and already overloaded across two endpoints — steering explicitly asks for it to be split.
  - `ddl-auto: validate` means a new entity without a matching Liquibase changeset is a **startup failure**, not a silent patch. Schema and entity must land together.
  - The test suite is unit-level with **no database and no Testcontainers**. Three acceptance criteria (3.5 concurrency, 6.1 durability, 6.2 atomicity) cannot be verified by the current test infrastructure. This is the single largest risk in the feature.
  - `MATCH` is a reserved word in the SQL standard and in PostgreSQL, so the table cannot be named `match`.

## Research Log

### Liquibase conventions and the next free changeset id

- **Context**: Two new tables are required; changesets are immutable once run, so the numbering and format must be right first time.
- **Sources Consulted**: `src/main/resources/db/changelog/changes/001-create-dog.sql`, `003-seed-demo-dogs.sql`, `004-legacy-dog-row.sql`, `db/changelog/db.changelog-master.yaml`, steering `tech.md`.
- **Findings**:
  - File `002-*.sql` does not exist: changeset `002-create-dog-preference` lives **inside** `001-create-dog.sql`. One file may hold several changesets, so file number ≠ changeset id.
  - Next free changeset id is `005`. Format is fixed: `--liquibase formatted sql`, blank line, `--changeset tinder4dogs:<NNN>-<kebab>`, `--comment: <lowercase sentence>`, SQL, `--rollback <statement>;`.
  - Identity is `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` — never `BIGSERIAL`.
  - Composite keys and FKs are **named table-level constraints**: `pk_<table>`, `fk_<table>_<target>`, with `ON DELETE CASCADE`.
  - No `CREATE INDEX` and no `CHECK` constraint exists anywhere in the repo; the absence of a `CHECK` on `dog.age` is deliberate (documented in `004`).
- **Implications**: New migration is a single file `005-create-matching.sql` holding changesets `005` and `006`, mirroring the `001` precedent. Uniqueness is expressed in SQL as a named constraint, not as a JPA `@UniqueConstraint`, matching how `pk_dog_preference` is done.

### Representing an undirected match

- **Context**: Requirement 3.6 states a match has no direction and both dogs see the same record; 3.4 and 3.5 require at most one match per pair regardless of arrival order or concurrency.
- **Sources Consulted**: Existing schema; standard relational practice for symmetric relations.
- **Findings**: Three candidate representations were considered (see Architecture Pattern Evaluation). Storing the pair in a **canonical order** (lower dog id first) reduces "undirected" to a plain two-column unique constraint, which the database can enforce without application-level locking.
- **Implications**: A small pure value object performs the ordering. Because it has no dependencies it is directly unit-testable, exactly like `MatchScoreService`.

### Concurrency: two simultaneous likes (3.5)

- **Context**: Both owners may like at the same instant. A read-then-write check (`SELECT` then `INSERT`) has a race window that produces two matches for one pair.
- **Sources Consulted**: `application.yaml` (default transaction isolation, i.e. PostgreSQL `READ COMMITTED`); Spring Data exception translation.
- **Findings**: Under `READ COMMITTED`, a check-then-insert cannot exclude a concurrent insert. The reliable mechanism is the **unique constraint itself**: attempt the insert, and treat the resulting integrity violation as proof that the other side won the race, then re-read the winner's row.
- **Implications**: `DataIntegrityViolationException` is part of the normal control flow, not an error path. This branch is unit-testable with a stubbed repository even though the constraint firing is not.

### Test infrastructure gap

- **Context**: Requirements 3.5, 6.1, and 6.2 are persistence-level guarantees.
- **Sources Consulted**: `pom.xml`, `MatchScoreServiceTest.kt`, steering `tech.md`, `.mise.toml`.
- **Findings**:
  - `spring-boot-starter-test` **is** present (JUnit 5, AssertJ, Mockito, spring-test). No Testcontainers, no H2, no MockK. `src/test/resources/` does not exist.
  - `mise run test` deliberately needs no database. Adding Testcontainers would make Docker a prerequisite for the test suite, contradicting that property.
  - Mockito is on the classpath but unused anywhere in the repo.
- **Implications**: Domain logic is verified by unit tests with stubbed repositories (Mockito), which covers the decision matrix, reciprocity, idempotency, and the race-handling branch. The **database-enforced** guarantees (unique constraint actually firing, rollback, durability) remain unverified by automated tests. Recorded as the top risk with a recommended follow-up rather than silently accepted.

### Naming collision on `MatchResponse`

- **Context**: The new feature needs a response type for a real (mutual) match, but `MatchResponse` already exists in `match/MatchController.kt`.
- **Sources Consulted**: `MatchController.kt`, steering `structure.md` ("Known Inconsistencies").
- **Findings**: Steering already flags this exact class: *"`MatchResponse` means two different things depending on the endpoint. Split it rather than extending the overload."* The class name does not appear in the JSON payload, so renaming it changes no API contract.
- **Implications**: Renaming the existing type into two intention-revealing names is a pure, zero-risk rename that resolves the collision and executes a fix steering already asked for. The alternative — awkwardly prefixing the new type — would leave the flagged inconsistency in place and make the new code read worse.

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| Canonical ordered pair (**selected**) | Store `low_dog_id`, `high_dog_id` with the smaller id first, under a unique constraint | Undirected-ness enforced by the database; single row per pair; simple queries | Lookup by one dog must check both columns, needing a second index | Ordering logic isolated in a pure, testable value object |
| Two mirrored rows | Insert one row per direction | Trivial one-column lookup | Two rows to keep consistent; "exactly one match" becomes an application invariant the DB cannot enforce; violates 3.6 in spirit | Rejected |
| Derive matches on the fly | No match table; compute reciprocity by self-joining decisions | No new table, no duplication risk | No creation timestamp (3.7 unsatisfiable); a later pass would retroactively erase history, contradicting 2.4 | Rejected |
| Application-level lock | Serialize match creation in code | Avoids relying on constraint violations | Does not survive multiple instances; heavier than the constraint it replaces | Rejected |

## Design Decisions

### Decision: Reciprocity is derived from decisions; the match is materialized

- **Context**: A match could be a stored fact or a query over decisions.
- **Alternatives Considered**:
  1. Derive on read — no match table.
  2. Materialize on write — a match row created at the moment reciprocity is detected.
- **Selected Approach**: Materialize. The match row carries its own creation timestamp and, once written, is independent of later changes to the underlying decisions.
- **Rationale**: 3.7 requires the creation moment, and 2.4 requires a match to survive a like being changed to a pass. A derived view cannot satisfy either: it would have no timestamp and would silently vanish when a decision is revised.
- **Trade-offs**: Introduces a second table that must stay consistent with the first — mitigated by creating both inside one transaction.
- **Follow-up**: Verify the match survives a like→pass revision (2.4).

### Decision: Outcomes are a sealed result type, not exceptions

- **Context**: A decision can fail because a dog is unknown (1.4) or because actor and target are the same (1.5). The repo has no `@ControllerAdvice`, so an `IllegalArgumentException` from `require` currently surfaces as an unstructured **500** — the wrong answer for both.
- **Alternatives Considered**:
  1. `require(...)` in the service, as `MatchScoreService` does.
  2. Add a `@ControllerAdvice` to translate exceptions.
  3. Return a sealed result type the controller exhaustively maps.
- **Selected Approach**: A sealed interface `DecisionOutcome` with one variant per outcome.
- **Rationale**: Option 1 produces a 500 for what are ordinary client errors. Option 2 is a structural change that steering says deserves its own commit, and would widen this spec's boundary. Option 3 keeps domain rules in the service (steering) while letting the controller choose status codes, and the Kotlin compiler enforces that every outcome is handled. This is the discriminated-union pattern the design principles require.
- **Trade-offs**: A new idiom for this codebase. Justified because the existing idiom yields incorrect status codes here.
- **Follow-up**: Keep `when` expressions exhaustive without an `else` branch, so a new outcome breaks the build rather than silently returning a wrong status.

### Decision: Liking is independent of scoring

- **Context**: `004-legacy-dog-row.sql` seeds "Nonna" with age -3, whom `canScore` rejects.
- **Selected Approach**: Decisions and matches never consult `MatchScoreService` (1.6, 5.6). Scoring remains confined to ranking candidate lists.
- **Rationale**: A like is an expressed human intent; a score is a computed suggestion. Coupling them would make corrupt profile data silently destroy real user actions.
- **Trade-offs**: A dog that can never be ranked can still be matched. Acceptable, and arguably correct.
- **Follow-up**: Assert explicitly that a dog with a negative age can both decide and be matched.

### Decision: Rename the overloaded `MatchResponse`

- **Context**: Name collision (see Research Log).
- **Selected Approach**: Split the existing type into `RankedCandidateResponse` and `PairScoreResponse`; the freed name `MatchResponse` denotes a real mutual match.
- **Rationale**: Executes a fix steering already requested; the rename is invisible to API clients because the class name is not serialized.
- **Trade-offs**: Touches `MatchController.kt`, a file otherwise outside this feature. Bounded to a rename with no behavioural change.
- **Follow-up**: Confirm no JSON field names change.

### Decision: Clock is injected

- **Context**: 3.7 and 5.3 depend on creation timestamps and ordering.
- **Selected Approach**: The service takes a `java.time.Clock`, defaulting to `Clock.systemUTC()`.
- **Rationale**: Makes timestamp and ordering behaviour deterministically testable without a database or sleeps.
- **Trade-offs**: One extra constructor parameter.

## Synthesis Outcomes

- **Generalization**: Like and pass are not two features but one `Decision` record with an enum value, so idempotency and revision (2.1, 2.2, 2.5) are handled once. The interface would accommodate a third verb (for example "super-like") without schema redesign; no such verb is implemented.
- **Build vs. adopt**: Nothing is built that the platform already provides. Uniqueness and atomicity are delegated to PostgreSQL constraints and Spring-managed transactions rather than reimplemented in Kotlin. No new dependency is introduced — `spring-tx` arrives with `spring-boot-starter-data-jpa`, and Mockito with `spring-boot-starter-test`.
- **Simplification**: Rejected a separate "reciprocity detector" component (it is one repository lookup inside the service); rejected a repository abstraction layer over Spring Data (single implementation, no second foreseeable one); rejected a `DecisionService`/`MatchService` split, since both operate on one transactional boundary and splitting would create shared ownership of match creation. The result is one service, two entities, two repositories, two controllers.

## Risks & Mitigations

- **Persistence guarantees are untested (3.5, 6.1, 6.2)** — the unique constraint, transactional rollback, and durability cannot be exercised without a database. *Mitigation*: unit-test the race-handling branch with a stubbed repository that throws; verify the constraint manually against a real database via `mise run db` before release. *Recommended follow-up*: a separate spec adding a Testcontainers-backed persistence test slice, which would make Docker a prerequisite for `mise run test` and therefore deserves its own decision.
- **`ddl-auto: validate` turns any entity/schema mismatch into a startup failure** — a column type or name drift stops the application. *Mitigation*: write the changeset and the entity in the same task and start the application against a real database once.
- **Changeset immutability** — an error in `005` cannot be edited after it has run anywhere. *Mitigation*: review the DDL before first run; fix any mistake with `007`.
- **`MATCH` is a reserved SQL word** — a table named `match` fails or requires quoting. *Mitigation*: the table is `dog_match`; the entity keeps the domain name `Match` via `@Table(name = "dog_match")`.
- **Reserved-word risk extends to future columns** — avoid `end`, `order`, `user` in this feature's schema. *Mitigation*: current column names are all safe.
- **Two FKs from `dog_match` to `dog` with `ON DELETE CASCADE`** — deleting a dog removes its matches. There is no delete endpoint today, so this is latent, and cascade is the behaviour the existing `dog_preference` table already chose.
